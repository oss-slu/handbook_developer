# Working Agreement Template

A working agreement is a conversation that produces a document, not the other way around. The value is in the team discussion about how you want to work together. The document captures the outcome so you can refer back to it when questions arise.

This template provides structure for that conversation. Your team should add sections that matter to you and remove ones that don't. A short, honest agreement that the team actually follows is worth more than a thorough one that sits in a file nobody reads. Every member should contribute to and sign the agreement.

```markdown
# Team Working Agreement

**Team:** [Team Name]
**Project:** [Project Name]
**Iteration:** [e.g., Spring 2026]
**Last Updated:** [Date]

## Team Members and Roles

- **Tech Lead:** [Name]
- **Developers:** [Names]
- **Client Contact:** [Name]

## Communication Norms

### Response Times
- **Slack messages:** [e.g., Within 4 hours during weekdays]
- **PR review requests:** [e.g., Within 24 hours]

### Preferred Channels
- **Quick questions and coordination:** [e.g., Slack #project-channel]
- **Technical discussions:** [e.g., GitHub issues and PR comments]
- **Client communication:** [e.g., Email with team cc'd]

### Meeting Schedule
- **Team meeting:** [Day/time, duration]
- **Client check-in:** [Frequency, day/time]

## Code Practices

- **Branching strategy:** [e.g., Feature branches from main]
- **Commit message format:** [e.g., Conventional commits, or team preference]
- **PR requirements:**
  - [e.g., At least 1 approval required]
  - [e.g., All tests passing]
  - [e.g., Description references issue]
- **Code review turnaround:** [e.g., Within 24 hours]
- **Testing requirements:** [e.g., Unit tests for new features]

## Collaboration Expectations

### Pair Programming
[When and how your team will pair. Frequency, scheduling approach.]

### Asking for Help
[When to ask, who to ask first, how to ask well.]

### Giving and Receiving Feedback
[How you'll handle code review feedback. How you'll handle interpersonal feedback.]

## Conflict Resolution

1. [e.g., Direct conversation between involved parties]
2. [e.g., Mediation by Tech Lead if not resolved]
3. [e.g., Involve program staff if needed]

## Definition of Done

A work item is complete when:

- [ ] All acceptance criteria met
- [ ] Code reviewed and approved
- [ ] Tests written and passing
- [ ] Documentation updated
- [ ] [Any additional team-specific criteria]

## Team Values

We commit to:

- [Value statement]
- [Value statement]
- [Value statement]

## Signatures

By signing below, we agree to uphold this working agreement:

- [Name, Date]
- [Name, Date]
```

## Guidance

- **Be specific.** "Within 4 hours" is better than "quickly."
- **Make it realistic.** Don't commit to norms you can't sustain.
- **Review regularly.** Update the agreement when something isn't working. The agreement serves the team, not the other way around.
- **Get buy-in.** Everyone should contribute, not just the Tech Lead. The agreement is stronger when it reflects the whole team's input.
- **Post it visibly.** Link from your project README and Slack channel description so it's easy to find.
