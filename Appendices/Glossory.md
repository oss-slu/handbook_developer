# Glossary

Terms used throughout this handbook and the broader program. Definitions are scoped to how these terms are used in Open Source with SLU.

## Team and Culture Terms

**Developer Empathy** - The principle that developers are people first. Respect for different skill levels, learning curves, and life constraints.

**Hungry, Humble, Smart** - A framework for effective team members. Hungry refers to motivation and initiative. Humble refers to willingness to learn and share credit. Smart refers to interpersonal awareness and effective collaboration.

**Servant Leadership** - A leadership philosophy focused on serving and enabling team members' growth and success rather than exercising authority. The approach practiced by Tech Leads in the program.

**Pair Programming** - A collaborative practice where two developers work together at one workstation. One writes code (driver) while the other reviews and thinks about the bigger picture (navigator). Roles switch frequently.

**Retrospective** - A regular team meeting for reflecting on recent work, identifying what went well, discussing challenges, and planning improvements to team processes.

**Working Agreement** - A collaboratively created document that establishes team norms, communication protocols, and shared expectations for how the team will work together. Created at the start of each iteration.

## Program Terms

**Open Source with SLU** - The program that develops software professionals through real-world open source software development, combining professional engineering practice with leadership development and community contribution.

**Developer** - A team member responsible for implementing features, writing code, participating in code reviews, and contributing to project success under the guidance of the Tech Lead.

**Tech Lead** - The team member responsible for technical leadership, mentorship, client relationships, and project management. Serves as the senior technical voice for the development team.

**Iteration** - A 16-week development cycle, typically aligned with an academic semester, during which teams work to deliver working software and achieve program objectives.

**Sprint** - A two-week development cycle within an iteration. Each sprint includes planning, development, code review, and a demo.

**Launch Sprint** - The final three-week sprint of the iteration, extended to accommodate end-of-iteration activities, final deliverable preparation, and presentations.

**Milestone** - A larger goal targeted for completion at a natural checkpoint in the iteration (midterms or end of semester). Milestones represent tangible, demonstrable value achieved across multiple sprints.

**Checkpoint Artifacts** - Deliverables due at specific points throughout the iteration that support team development. Examples include Working Agreements, sprint close reports, and demo videos.

**Exception Report** - A written account submitted when you deviate from an expected norm, such as a missed deadline or a deliberate process adaptation. Documents what happened, why, and what changes going forward.

## Product Terms

**Product Strategy** - A document capturing the product vision, target users, problem statement, and roadmap. Guides both current and future development.

**User Story** - A short description of a feature from the user's perspective, typically formatted as "As a [user type], I need [goal], so that [reason]."

**Value Proposition** - A clear statement of the benefits a product provides to users. Explains why someone should use the software and what problems it solves.

## Technical Terms

**Acceptance Criteria** - Specific boolean conditions that must be true for a piece of work to be considered complete. Written as checkboxes in GitHub issues.

**Architecture Decision Record (ADR)** - A document that captures an important technical decision, the context behind it, alternatives considered, and expected consequences. Preserves the "why" behind technical choices.

**Backlog** - A prioritized list of issues representing work that needs to be done. The backlog is the source of work items for sprint planning.

**Branch** - A parallel version of a repository that allows developers to work on features or fixes independently before merging changes back into the main codebase.

**CI/CD (Continuous Integration / Continuous Deployment)** - Automated processes that build, test, and deploy code changes. Helps maintain code quality and enables rapid, reliable delivery.

**Code Review** - The practice of examining code changes before they are merged. Catches bugs, shares knowledge, and raises the team's standard of work.

**Draft PR** - A pull request opened before the work is complete, used to give the Tech Lead early visibility and create a place for feedback before full review.

**Feature Branch** - A branch created for developing a specific feature or fix, kept focused and short-lived. Typically maps one-to-one with an issue.

**Feature Flag** - A mechanism to enable or disable functionality without deploying new code. Used to merge incomplete work safely or to control rollout of new features.

**Main Branch** - The primary branch containing the stable, production-ready version of the code. All feature branches merge into main.

**Merge Conflict** - A situation where Git cannot automatically reconcile differences between two versions of code, requiring manual resolution.

**Pull Request (PR)** - A proposed set of changes submitted for review. Pull requests enable code review, discussion, and collaboration before changes are merged.

**Technical Debt** - The implied cost of additional work caused by choosing a quick solution now instead of a better approach that would take longer. Must be managed to maintain development velocity.

**Velocity** - A measure of the amount of work a team completes during a sprint. Helps predict future capacity and plan realistic commitments.
